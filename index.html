Layered Architecture & Monolithic Architecture

Understanding how code is logically structured into tiers (Layered) versus how an application is packaged and deployed as a single unit (Monolithic).

1. Layered Architecture (N-Tier)

Presentation Layer: Handles HTTP requests, input formatting, authentication checks, and renders UI or JSON responses.
  • Separation of concerns & clean code structure
  • Better maintainability & isolated unit testability
  • Encourages reusability across enterprise apps

Key Characteristics & Advantages

  • Domain Decomposition: Organized around business capabilities.
  • Database per Service: Strict data ownership; no shared DB coupling.
  • Independent Scaling: Scale hot services (e.g., Order) independently.
  • Fault Isolation: Failure in one service won't crash the entire platform.
  • Polyglot Stack: Use the best language/DB per service.

Challenges & Real-World Adopters

  • Distributed system complexity (tracing, logging, service mesh).
  • Network latency & eventual data consistency across services.
  • Higher infrastructure & DevOps automation cost.
Netflix Uber Amazon Swiggy / Zomato Nykaa

Page 5 // Asynchronous Messaging & Brokers

Message Queue & Pub/Sub Patterns

Buffering traffic spikes, distributing background tasks, and streaming real-time events using durable message brokers.

📬 Messaging Topology & Kafka Consumer Group Simulator

🎯 Message Delivery Guarantees

At Most Once

Fire-and-forget. Messages may be lost on failure, never duplicated. Used for best-effort metrics/logs.

At Least Once (Most Common)

Guaranteed delivery via retries & ACKs, but duplicates can occur. Requires idempotent consumers.

Exactly Once

Each message processed strictly once. Hardest to achieve; requires transactional outbox + idempotency.

CQRS & Event Sourcing

Separating write commands from read queries (CQRS) and storing every state mutation as an append-only sequence of domain events (Event Sourcing).

Benefits of CQRS + Event Sourcing

  • Independent Scaling: Scale read replicas independently from write nodes.
  • Complete Audit Trail: Every historical state change is preserved forever.
  • Time-Travel & Replay: Rebuild corrupted read views or spin up new analytics projections by replaying events.

Trade-offs & Ideal Use Cases

  • Eventual consistency between Write Model and Read Projection.
  • Higher architectural complexity; overkill for simple CRUD apps.
Banking & Payments E-Commerce Orders Flight/Hotel Bookings Version History

🗂️ Table Partitioning (Single DB Instance)

Divides a large table (e.g., Orders) into smaller manageable physical parts within the same database for faster queries and easy archival:

  • Range Partitioning: By date intervals (P1: Jan–Mar, P2: Apr–Jun, P3: Jul–Sep).
  • Hash Partitioning: By hash of userId for uniform distribution.
  • List Partitioning: By discrete values like Region (US, EU, APAC).

📈 Vertical vs. Horizontal

Vertical (Scale Up): Upgrade single box (4GB → 64GB RAM). Simple, but hits hardware ceiling.

Horizontal (Scale Out): Add more stateless instances behind a Load Balancer. Infinitely scalable & fault tolerant.

🚦 Rate Limiting Algorithms

  • Fixed Window: e.g., 100 req/min counter.
  • Sliding Window: Smooth rolling timestamp check.
  • Token Bucket: Allows controlled traffic bursts.
  • Leaky Bucket: Smooths output to fixed rate.

🚢 Bulkhead Pattern

Inspired by ship compartments: isolates thread pools & connection pools per downstream dependency (Module A, B, C) so one slow service cannot exhaust all threads.

Additional Traffic Control Patterns

🔁 Retry Pattern (Exponential Backoff)

Automatically re-attempt transient failures (5xx, network timeouts) with increasing delays + jitter and a strict max retry cap:

Attempt 1 (0s) → Retry 1 (1s) → Retry 2 (2s) → Retry 3 (4s) → Max Cap (8s)

🔑 Idempotency, Timeout & Fallback

  • Idempotency-Key: Client sends unique UUID (e.g., Idempotency-Key: abc123). Retries return the cached result instead of charging twice.
  • Timeout: Bound wait duration on remote calls to prevent thread starvation.
  • Fallback: Serve graceful degraded response (cached catalog, default recommendations) when primary call fails.

Reliability & Fault Tolerance Patterns

Eliminating Single Points of Failure (SPOF), surviving regional outages, and achieving 99.99% availability in production.

Reliability vs. Availability vs. Fault Tolerance

TermDefinitionReal-World Benchmark
ReliabilitySystem performs its intended function accurately and consistently over time without data corruption.99.99% successful transaction integrity
AvailabilityPercentage of time the system is operational and accessible when requested.99.99% uptime (~52 mins downtime/year)
Fault ToleranceSystem continues operating seamlessly even when underlying servers or zones crash.Zero user impact when 1 AZ goes offline

🌍 Multi-Region Deployment & Failover Simulator

⏱️ Disaster Recovery Metrics (RPO & RTO)

  • RPO (Recovery Point Objective): Maximum acceptable amount of data loss measured in time (e.g., RPO = 5 mins means backups/replication happen at least every 5 mins).
  • RTO (Recovery Time Objective): Maximum acceptable downtime to restore service after an outage (e.g., RTO = 30 mins).
  • Strategies: Periodic S3 snapshots, cross-region replication, automated DNS failover.
